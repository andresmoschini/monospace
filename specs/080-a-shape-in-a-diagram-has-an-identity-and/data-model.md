# Data model: a shape has an identity, and the order can change

What this slice adds to `monospace-diagram`, and what it changes in `monospace-cli`. Everything spec
079 built stays as it is unless it is named here. Why each type is shaped this way is in
[research.md](research.md); the public surface alone is in
[contracts/diagram-api.md](contracts/diagram-api.md).

## `ShapeId` — new, public

A shape's identity, generated by the diagram and unique within it.

| Part       | Type               | Visibility | Meaning                                                |
| ---------- | ------------------ | ---------- | ------------------------------------------------------ |
| the number | `u32`              | private    | The ordinal the diagram handed out: 1 for the first    |
| `Display`  | `#` and the number | public     | `#1`, `#2`, and so on — how an identity reads (FR-001) |

Derives `Clone`, `Copy`, `Debug`, `PartialEq` and `Eq`. Equality is what `forward` and `backward`
search with, and it is equality of the number: two identities are the same identity when they name
the same addition to the same diagram.

Rules:

- There is no way to build one (FR-003). The field is private, no constructor is exposed, and
  neither `From<&str>` nor `FromStr` is implemented. `Display` is one-way.
- Nothing reads the number back out. A caller can print an identity and compare two; that is all.
- It carries no reference to the diagram that made it, so an identity from another diagram is a
  well-formed value that simply matches nothing here (edge case 3).

## `Placed` — new, private to the crate

One entry of a diagram's order: a shape and the identity the diagram gave it.

| Field   | Type      | Meaning                                                  |
| ------- | --------- | -------------------------------------------------------- |
| `id`    | `ShapeId` | The identity handed back by the `add` that placed it     |
| `shape` | `Shape`   | The figure itself, unchanged from spec 079 and untouched |

It exists so that the pairing is a type rather than a convention (research.md Q2). It is never named
in the public surface, so a later slice can add a field to it without that being a breaking change.

## `Diagram` — changed

| Field    | Type          | Visibility | Meaning                                                      |
| -------- | ------------- | ---------- | ------------------------------------------------------------ |
| `shapes` | `Vec<Placed>` | private    | The order. The **last** element is the front, as in spec 079 |
| `next`   | `u32`         | private    | The ordinal the next `add` will use, after incrementing it   |

`#[derive(Default)]` still gives the empty diagram: no shapes, and a counter of 0 whose first use
increments to 1.

### `add(shape) -> ShapeId`

1. Increment `next`.
2. Build the identity from its new value.
3. Push `Placed { id, shape }` onto the end of `shapes`, which is the front of the order (FR-005,
   unchanged from spec 079).
4. Return the identity (FR-002).

Adding the same shape value twice runs this twice and produces two identities, because nothing here
looks at the shape (user story 1, scenario 3).

### `forward(id)` and `backward(id)`

Both take an identity, return nothing, and cannot fail (FR-009).

1. Find the index of the entry whose `id` equals the argument. No entry — return, having changed
   nothing (FR-009).
2. `forward`: the entry is already the last element — return, having changed nothing (FR-010).
   Otherwise swap it with the element after it, one place nearer the front.
3. `backward`: the entry is already the first element — return, having changed nothing (FR-010).
   Otherwise swap it with the element before it, one place nearer the back.

A swap of two neighbors moves each of them one place, so `forward` on the back one of a pair and
`backward` on the front one are the same change named from either side (user story 2, scenario 2),
and either one undoes the other (scenario 6). Nothing else is touched: the shapes, their parameters
and their identities are the values that were there, moved (FR-011).

### `draw(buffer)`

Unchanged in what it does, and now visits `Placed` values, drawing `placed.shape`. Still front to
back, still one `Layer` bound to `StampMode::Below`, still `&self`.

### What `Diagram` still does not have

No way to read its shapes, its identities or its order back (FR-012). `draw` remains the only
observation, which is what every test below uses.

## The `monospace-cli` side

### `Description::into_diagram` — changed

Returns `(Diagram, Option<ShapeId>)`: the diagram built from `shapes` in order, and the identity of
the **first** entry — the back-most shape, since each addition goes in front of the last (FR-015).
`None` when `shapes` is empty.

Position in the file is the only thing that identifies it. The description format gains no field and
the description types stay private to the crate (FR-019).

### `Description::buffer` — removed

Its one line, `Buffer::new(origin, size)`, moves to the call site, which needs two buffers from one
description that `into_diagram` consumes (research.md Q7). This is structural: same behavior, one
fewer helper, its own `refactor` commit.

### `render_description` — changed

```text
window()                       -> origin, size
into_diagram()                 -> diagram, back-most identity
caption 1, draw into a buffer, render
blank line
forward(back-most identity)    -- demonstration-only assumption, FR-016
caption 2, draw into a second buffer, render
```

The first picture is byte for byte what this function returned before the feature, because the
diagram it draws is built the same way from the same description and rendered with the same catalog
(FR-014). The output around it is new.

Where the identity is `None` — a description holding no shapes — the move is skipped and the second
picture is drawn from the same diagram, so the two pictures are identical (user story 3, scenario
4). A description holding one shape takes the move, which changes nothing because that shape is
already at the front.

The comment FR-016 asks for sits at the `forward` call: moving the first entry shows something only
because the shipped demonstration's first two entries are two partially overlapping opaque boxes,
and that is an assumption about the demonstration rather than a rule about descriptions.

## The shipped demonstration

`crates/monospace-cli/assets/demo.json` is unchanged (FR-017). Its first two entries are already two
opaque boxes at `(0, 0)` and `(2, 1)`, both 4 by 3 and filled, so they overlap and the move between
them is visible.
